# Learning Backlog and Research Notes

Це каталог для посилань, статей, ідей нових модулів і пропозицій розширити наявні матеріали. Тут зберігаємо не копії статей, а навігацію до джерел, короткі тези, оцінку корисності та зв'язок із майбутнім навчальним планом.

## Структура

- [roadmap.md](roadmap.md) — теми, які варто додати, перевірити або використати у запланованих проєктах;
- `sources/<technology>/theory.md` — концептуальні статті, документація й довідкові пояснення;
- `sources/<technology>/examples.md` — короткі практичні приклади, tutorials і labs;
- `sources/<technology>/e2e-projects.md` — production/E2E проєкти та великі case studies;
- `architectures/<technology>/<topic>.md` — окремі архітектури, надіслані користувачем або зібрані з кількох джерел;
- `topics/` — аналіз прогалин у наявних навчальних матеріалах і пропозиції щодо їх розвитку;
- `inbox/` — за потреби тимчасові нерозібрані пакети, коли тему ще не визначено. Після сортування перенеси зміст у тематичну нотатку й прибери тимчасовий пакет.

Не створюй окрему нотатку на кожне посилання. Групуй джерела за технологією та типом використання, зберігай канонічний URL один раз і позначай дублікати або допоміжні дзеркала. У source-list для кожного посилання вкажи назву, короткий опис, користь, статус перевірки й пов'язаний модуль/матеріал.

## Як додавати матеріали

У новому чаті передай посилання або текст разом із таким запитом:

```text
Прочитай HANDOFF.md і docs/learning-backlog/README.md.
Оформи надані нижче посилання/матеріали в learning backlog:
- згрупуй і дедуплікуй джерела;
- класифікуй кожне як theory, practical example, E2E/production case або architecture;
- створи чи онови відповідні тематичні файли, не складай різні типи матеріалу в один список;
- додай короткі тези, користь для навчання та статус перевірки;
- пов'яжи їх із наявними модулями або roadmap-ідеями;
- відділи перевірені факти від тверджень, які треба звірити;
- не перенось повний текст статей у репозиторій.
Матеріали: <посилання або вставлений текст>
```

Для кожного джерела, де це доступно, фіксуй:

- назву, автора/видавця, дату публікації або оновлення;
- прямий URL на першоджерело; дзеркала й агрегатори позначай як допоміжні;
- головну тезу своїми словами та конкретну користь для roadmap;
- цільовий модуль, існуючий файл або потенційний план;
- стан перегляду й окремі claims, які потребують перевірки за актуальною документацією.

Рекомендовані статуси: `new`, `triaged`, `planned`, `integrated`, `rejected`. `planned` не означає, що зміна схвалена або вже реалізується: це лише кандидат для наступного планування.

## Якщо надіслано великий текст

Використовуй текст як матеріал для аналізу, але записуй у репозиторій короткий авторський переказ, висновки та посилання. Не копіюй цілі статті, великі фрагменти чи їхній повний виклад у публічний Git. Цитуй лише коротко, коли це справді потрібно, з чітким посиланням на джерело.

Для синтетичних оглядів, AI-відповідей або добірок з багатьма цитатами зберігай їх як **неперевірені тези**, а не як джерело істини. Розбий claims на окремі питання, знайди першоджерела та перевір змінні технічні деталі в актуальній офіційній документації. Позначай маркетингову позицію, застарілі приклади, непідтверджені цифри та недоступні сторінки.

## Якщо надіслано готову архітектуру

Збережи її як окремий файл у `architectures/<technology>/<descriptive-topic>.md`, щоб її можна було знайти за темою без пошуку серед звичайних статей. Файл має містити назву, короткий контекст/use case, авторський опис діаграми й потоку даних, source links, що саме перевірено, припущення/відкриті питання, trade-offs і посилання на модуль або E2E-проєкт.

Якщо користувач передав власну діаграму/файл, збережи оригінал лише коли формат і права дозволяють та він потрібен для подальшої роботи; поруч створи Markdown-навігатор. Для чужої опублікованої діаграми не копіюй зображення в репозиторій: збережи URL, підпис і власний текстовий/Mermaid переказ без відтворення захищеної графіки.

## Як backlog переходить у навчання

1. Додай або онови source card у правильній категорії: theory, example, E2E або architecture.
2. Окремий architecture note створюй для завершеної системної схеми/дизайну, а не для кожної статті з діаграмою.
3. Додай roadmap-рядок лише тоді, коли є конкретна дія: новий матеріал, перегляд чинного або внесок у запланований проєкт.
4. Коли робота почнеться, звірся з локальними README, шаблонами й handoff-ами. Перевір, що тема ще не покрита.
5. Після інтеграції створи з навчального матеріалу зворотне посилання на потрібну картку або джерело й познач roadmap як `integrated`.
6. Не змінюй існуючий модуль лише тому, що з'явилося посилання. Спершу визнач конкретну прогалину й цінність для навчального маршруту.

Для Snowflake E2E зважай на спеціалізований [handoff](../../16-cloud-databases/01-snowflake/end-to-end-projects/HANDOFF.md). Він є джерелом актуального стану проєктів; ця папка зберігає дослідницькі ідеї й посилання.
