# Підсумки реалізації end-to-end проєктів

Фінальні висновки після написання кожного проєкту: що зроблено, на чому тримається дизайн, що перевірено і де найімовірніше будуть проблеми при першому реальному запуску. Файл оновлюється після кожного нового проєкту.

Важливо для всіх проєктів: SQL, хмарні скрипти й конектори перевірені статично (рендеринг через `run_sql.sh`, синтаксис, тести Python). Наживо проти Snowflake, Azure, AWS чи Kafka вони не запускались. Перший реальний прогін — це частина навчання; записуй розбіжності в лог проєкту.

## P04 — Wikimedia → файли → Snowpipe

- **Шлях даних:** Python-producer пише мікробатчі NDJSON.gz + маніфест на кожен файл у ADLS → Event Grid → Storage Queue → Snowpipe → RAW (`VARIANT` + метадані файлу) → stream + serverless task з `MERGE` → STG → dynamic table → MART.
- **Ключові рішення:**
  - імена файлів унікальні й ніколи не перезаписуються, бо Snowpipe не перезавантажує вже бачене ім'я;
  - дедуплікація за `meta.id` у staging, бо Snowpipe дає ідемпотентність на рівні файлу, а не події;
  - `ON_ERROR = SKIP_FILE`, щоб файл був одиницею звірки;
  - звірка з маніфестом продюсера виявляє файли, які Snowflake не бачив;
  - serverless task замість складу для частих коротких запусків; lag dynamic table 5 хв як свідомий компроміс вартості.
- **Azure основний, AWS варіант** (S3 → SQS, IAM role з external ID).
- **6 failure drills:** дублікат вмісту, битий рядок, зміна схеми, пізні події, перезапис того самого імені, втрачене сповіщення.
- **Перевірено:** 3 unit-тести продюсера, smoke-запуск продюсера і chaos-скрипта локально, рендеринг усіх SQL, синтаксис скриптів і JSON-політик.
- **Ризики першого запуску:** consent і RBAC в Azure (затримка поширення ролей), фільтр Event Grid, модель тарифікації Snowpipe.

## P14 — Kafka connector → Snowpipe Streaming

- **Затримка.** Дані з'являються в Snowflake за секунди, без проміжних файлів.
- **Без дублів.** Кожен офсет із Kafka потрапляє в таблицю рівно один раз: Snowflake зберігає останній записаний офсет разом із даними. Це перевіряє окрема view по кожній партиції — дублі та пропущені офсети.
- **Безпека:**
  - конектор логіниться окремим сервісним користувачем `P14_KAFKA_SVC` (`TYPE = SERVICE`, лише key-pair);
  - роль конектора володіє рівно однією таблицею, і після її створення в неї забирається право створювати нові.
- **Биті повідомлення** йдуть в окремий DLQ-топік і не зупиняють конектор.
- **Live-view** показує останні 5 хвилин у секундній свіжості.
- **Скрипт `connector.sh`** керує конектором: apply, status, pause, resume, restart, delete.
- **7 failure drills:** рестарт Kafka Connect, битий запис, зміна схеми, дубль події, зламана авторизація, ребаланс, пікове навантаження.

## P15 — Kafka → lake → Snowpipe

- **Власний `lake_writer.py`** записує Kafka у файли так само, як це роблять продакшн-конектори. Три правила:
  - межі файлів залежать тільки від самих записів — від часових міток Kafka і їх кількості;
  - в імені файлу є топік, партиція та перший і останній офсет;
  - офсет у Kafka фіксується лише після того, як файл записаний.
- **Наслідок:** якщо writer впаде між записом файлу й фіксацією офсету, після перезапуску він згенерує той самий файл, побачить, що той уже є, і пропустить його. Дублів не буде.
- **Звірка.** Окремі маніфести, як у P04, не потрібні: офсети в Kafka йдуть підряд, тож пропущений файл одразу видно як пропущені офсети.
- **Replay з lake** через `COPY ... FORCE = TRUE` в окрему таблицю. Так можна перезавантажити будь-яку годину навіть після того, як дані зникли з Kafka.
- **Варіанти для продакшну** описані в README: Event Hubs Capture, Connect-конектор у сховище, Flink → Iceberg.

## P01 — Cricket JSON → bronze / silver / gold

- **Шлях даних:** архів Cricsheet (усі ODI з 2000 року) → `prepare_batches.py` розкладає матчі по папках `year=YYYY` → `PUT` в internal stage з directory table → граф задач `LOAD_RAW → BUILD_SILVER → BUILD_GOLD`.
- **Ключові рішення:**
  - `COPY` із задачі, а не Snowpipe: дані приходять пакетами, а виправлений файл із тим самим ім'ям `COPY` перезавантажує (інша контрольна сума), Snowpipe — ні;
  - silver будується в одній транзакції зі stream: batch-таблиця фіксує вміст stream, при помилці все відкочується, і пакет лишається в stream на наступний запуск;
  - `MERGE` враховує `meta.revision`: старіша версія матчу не перезапише новішу;
  - deliveries матчу перебудовуються повністю, а не мерджаться по м'ячу — у джерела немає стабільного ключа м'яча;
  - gold перераховується повністю (`INSERT OVERWRITE`): секунди на XS, без складних інкрементальних випадків.
- **Доменні правила в SQL:** wide не рахується як м'яч для бетсмена, bye/leg bye не йдуть на боулера, run out і retirements не є хвіртками боулера, retired hurt не є out, super over виключено зі статистики гравців.
- **Факти з реальних даних (2023–2025):** 606 матчів, 573 з переможцем, 24 без результату, 9 нічиїх, 12 super-over іннінгів; до 11 записів про вибуття в іннінгу, бо retirements записані як wickets. Через це data quality check виключає retirements.
- **6 failure drills:** запуск без нових даних, дельта, виправлений файл, битий файл, зламаний silver task, застарілий stream.
- **Перевірено:** 2 unit-тести `prepare_batches.py`, реальне завантаження архіву й розкладка по роках, синтаксис скриптів, Mermaid, посилання.
- **Ризики першого запуску:** повний перший прогін графа займе кілька хвилин; зміна задач потребує призупинення кореневої задачі; якщо граф простоїть довше за retention, stream стане stale і silver треба перебудувати з RAW.

## P02 — Weather API → Snowflake → ноутбуки

- **Шлях даних:** Open-Meteo archive API (6 міст на 4 континентах, 2016 — минулий тиждень) → один JSON на місто й рік з полем `_source` → `PUT` в internal stage → `COPY` в RAW → STG погодинно → MART views → один ноутбук, що працює в Snowflake Notebooks, локальному Jupyter і Deepnote.
- **Ключові рішення:**
  - API повертає паралельні масиви; один `FLATTEN` по `hourly.time` + доступ за `[t.index]` розгортає всі змінні за один прохід;
  - зберігаємо UTC, у локальний час переводимо у view через `CONVERT_TIMEZONE` для кожного міста; день за UTC змішав би два локальні дні Сіднея;
  - аналітичні визначення (локальний день, кліматологія, аномалія, z-score, heavy rain) живуть у SQL views, а не в клітинках ноутбука;
  - кліматологія вимагає щонайменше 5 років на день року, інакше z-score нестабільний;
  - повторне завантаження року безпечне: RAW зберігає всі версії, STG бере останню через `QUALIFY`;
  - перша клітинка ноутбука пробує `get_active_session()`, інакше створює сесію з іменованого підключення; прапорець `IN_SNOWFLAKE` закриває локальну сесію наприкінці;
  - ноутбук тягне в pandas лише агрегати (сотні рядків), а не погодинну таблицю.
- **Знахідка під час написання:** `_source.fetched_at` змінює вміст файлу, тож навіть повторно завантажений минулий рік `COPY` завантажить знову. STG від цього захищений, а RAW росте — це винесено в drill.
- **Виправлено під час перевірки:** stage для ноутбука створювався пізніше, ніж його треба було завантажити; перенесено в `01_raw.sql`.
- **5 analysis drills:** день за UTC, неповний рік, повторне завантаження, забута відкрита сесія ноутбука, закоротка кліматологія.
- **Перевірено:** 3 unit-тести fetch-скрипта; живий запит до API (Київ і Сідней, 2024: 8784 години, без пропусків); валідний JSON ноутбука і синтаксис усіх 8 code-клітинок; синтаксис shell-скриптів.
- **Ризики першого запуску:** `altair` треба додати в Packages ноутбука; ноутбук, створений через SQL, потребує `ADD LIVE VERSION FROM LAST`; `.ipynb` треба вантажити без стиснення; відкрита сесія ноутбука тримає склад увімкненим.

## P03 — Wikipedia pageviews → serving layer → Streamlit in Snowflake

- **Шлях даних:** Wikimedia REST API (top-1000 статей за день і денні суми переглядів для en, de, uk) → JSON-файли з `_source` → `PUT` → `COPY` в RAW → STG (два рівні `FLATTEN`) → MART serving tables → Streamlit-застосунок у Snowflake.
- **Ключові рішення:**
  - три ролі: `P03_OWNER` володіє даними, `P03_APP_OWNER` володіє застосунком і своїм stage та має `SELECT` лише на MART, `P03_VIEWER` має тільки `USAGE` на застосунок;
  - застосунок працює з правами власника: глядач отримує відповіді, але не має доступу до жодної таблиці;
  - головні сторінки та службові namespaces (`Special:`, `Spezial:`, `Спеціальна:`, `Wikipedia:`, `Файл:`…) виключаються через довідкові таблиці; фільтр «є двокрапка» не годиться, бо є статті на кшталт `Ramayana:_Part_1`;
  - при повторному завантаженні дня перемагає весь останній список, а не окремі статті;
  - serving tables перебудовуються з `COPY GRANTS`, тож застосунок не втрачає доступ під час перезавантаження;
  - trending рахується лише з днів, коли стаття була в топі; це зміщення пояснено прямо в застосунку;
  - усі запити із введенням користувача йдуть через bind-параметри; результати кешуються на 10 хвилин;
  - версія Streamlit зафіксована в `environment.yml`; деплой — окремий скрипт, бо `CREATE STREAMLIT ... FROM` копіює файли один раз.
- **Факти з реальних даних:** списки містять від 987 до 1000 записів; головна сторінка завжди на 1 місці; фільтр прибирає 8–13 записів на день; дублікатів статей у списку немає; незапубліковані дні повертають 404.
- **6 failure drills:** відкликаний grant, перебудова без `COPY GRANTS`, глядач пробує читати таблицю, застарілий кеш, upload без deploy, спроба SQL-ін'єкції.
- **Перевірено:** 5 unit-тестів fetch-скрипта; живий fetch для uk і de (повторний запуск пропускає наявні дні); фільтр контенту перевірено на реальних списках; 2 smoke-тести застосунку через Streamlit `AppTest` з фейковою сесією (рендеринг усіх вкладок і перевірка, що текст пошуку не потрапляє в SQL); синтаксис shell-скриптів.
- **Ризики першого запуску:** гранти для перегляду застосунку (якщо Snowsight не покаже застосунок `P03_VIEWER`, перевір `USAGE` на базу, схему й застосунок); версія Streamlit з `environment.yml` має бути в списку підтримуваних; файли застосунку треба вантажити без стиснення; кожна відкрита вкладка застосунку тримає склад увімкненим.

## Виправлення в P01 після перевірки документації Snowflake

- **Що було не так:** задачі графа P01 лежали в трьох схемах (`RAW.LOAD_RAW`, `STG.BUILD_SILVER`, `MART.BUILD_GOLD`). Snowflake вимагає, щоб усі задачі одного графа мали одного власника й лежали в **одній схемі**. Граф не створився б при першому запуску.
- **Що зроблено:** усі три задачі перенесено в `OPS` (`OPS.LOAD_RAW`, `OPS.BUILD_SILVER`, `OPS.BUILD_GOLD`); оновлено SQL, QUICKSTART, 03, 05 і drills. У P05–P07 задачі одразу лежать в окремій схемі (`PIPE` або `OPS`).

## P05 — TPC-H → streams і tasks → CDC

- **Шлях даних:** `SNOWFLAKE_SAMPLE_DATA.TPCH_SF1` → копія замовлень за 1997 рік у `SRC` → процедура `OPS.SIMULATE_DAY` щоразу додає наступний реальний день TPC-H, виконує замовлення, коригує знижки на минулих рядках, редагує клієнтів і скасовує замовлення → streams → граф задач у `PIPE` → `CORE` і `MART`. Паралельно ті самі цифри будують dynamic tables для порівняння.
- **Ключові рішення:**
  - один stream на кожного споживача;
  - вимір клієнтів будується з рядків stream: старий образ оновлення (`DELETE` з `ISUPDATE`) відкидається, видалення стає soft delete;
  - факт замовлень будується через перерахунок зачеплених ключів: ключі з двох streams збираються одним `INSERT` у транзакції, і кожне таке замовлення перераховується з поточного стану через одну view. Повторний запуск дає той самий результат, на відміну від додавання дельт;
  - `MERGE` пропускає оновлення, які нічого не змінюють, щоб stream на факті не роздувався;
  - stream на факті дає вітрині дати, які змінилися, зокрема стару дату скасованого замовлення;
  - корінь графа запускається з `WHEN SYSTEM$STREAM_HAS_DATA`: якщо змін немає, обчислення не стартує;
  - finalizer пише в журнал кількість розбіжностей звірки після кожного запуску, зокрема невдалого;
  - streams створюються до першого знімка, а не після.
- **6 failure drills:** запуск без змін, падіння посеред графа, другий споживач того самого stream, повтор із дельтами, stale stream, сплеск змін (tasks проти dynamic tables).

## P10 — GH Archive → Airflow → Snowflake → архів у Parquet

- **Шлях даних:**
  - Airflow 3.4 у Docker (LocalExecutor, Postgres) запускає годинний DAG: сенсор чекає файл години на GH Archive → файл без змін кладеться в landing (internal stage, Azure Blob або S3) → `CALL OPS.LOAD_HOUR` → `CALL OPS.BUILD_HOUR` → перевірка години;
  - денний DAG чекає 24 готові години в `OPS.HOUR_LOG` → `BUILD_DAY` (MART і профіль джерела) → `ARCHIVE_DAY` (Parquet в архівний контейнер, читання назад, маніфест) → `PURGE_HOT`. Паралельно окрема задача перевіряє drift джерела.
- **Ключові рішення:**
  - одиниця роботи — година файлу: один запуск DAG, один об'єкт у landing, один перезапис RAW і STG, один рядок журналу;
  - Airflow вирішує «коли», Snowflake — «що». DAG викликає п'ять процедур `EXECUTE AS OWNER`; роль сервісного користувача `P10_AIRFLOW_SVC` має лише `USAGE` на них і `SELECT` на журнали — таблиць не бачить;
  - `LOAD_HOUR` спершу робить `LIST` файлу (бо `COPY` неіснуючого шляху «успішно» вантажить 0 файлів), потім видаляє годину і вантажить через `COPY ... FORCE = TRUE`. Load metadata відповідає на «чи вантажили цей файл», а не «чи є ця година в таблиці»;
  - кожна перебудова звіряє вхід із журналом і падає замість того, щоб видати менший результат: `BUILD_HOUR` проти RAW, `BUILD_DAY` проти STG, `ARCHIVE_DAY` проти `DAY_LOG`;

  - `catchup=False`, історія — лише через `airflow backfill create`; `start_date` (2025-01-01) — нижня межа backfill;
  - пули `gharchive_http` і `snowflake_p10` по 4 слоти обмежують кожен спільний ресурс для всіх DAG разом, а не лише для одного;
  - повноту дня денний DAG читає з даних (`OPS.HOUR_LOG`), а не зі статусів годинного DAG — так враховуються backfill і ручні перезавантаження;
  - архів: `REMOVE` префікса дня → unload Parquet → `COUNT` і `HASH_AGG(EVENT_ID)` з файлів порівнюються зі STG → маніфест → `VERIFIED`. Видаляються лише перевірені дні старші за 30 днів. Без `REMOVE` повторний unload з меншою кількістю файлів лишив би старі;
  - lifecycle зупиняється на онлайн-рівнях (Azure cold, S3 Glacier Instant Retrieval): archive tier і Glacier Flexible Retrieval Snowflake не прочитає без відновлення;
  - drift — окрема кінцева задача: стає червоною, але не блокує архів і очищення.
- **Знахідки на живих даних (вибірки 2024-11 … 2026-11):**

- **Ризики першого запуску:**
  - Docker на цій машині відсутній, тож `docker compose up` не запускався: найімовірніші місця — права на `logs/` (AIRFLOW_UID) і перший `airflow db migrate`;

## P11 — WFP, ECB, World Bank → Function/Lambda → Snowpark → Power BI

- **Шлях даних:**
  - Azure Function (Flex Consumption, таймер 06:00 UTC, managed identity) або AWS Lambda (EventBridge Scheduler, execution role) щодня перевіряє три джерела й кладе в `landing/markets/` лише нові версії файлів;
  - далі Event Grid → одна черга → три pipe → RAW (усі версії) → о 06:30 задача з `WHEN SYSTEM$STREAM_HAS_DATA` → Snowpark-процедура перебудовує CORE → MART (зірка з view) → семантичне view `SEM.FOOD_PRICES` і Power BI (Import, key pair).
- **Ключові рішення:**
  - **стріму немає свідомо:** джерела оновлюються раз на місяць або рік; функція за розкладом коштує копійки, а Kinesis чи Event Hubs платилися б щогодини даремно;
  - **версія в імені файлу:** для WFP — `last_modified` з метаданих HDX, для ECB і World Bank — хеш вмісту. Запис «створити, якщо немає» (Blob `overwrite=False`, S3 `If-None-Match: *`). Повторний запуск нічого не кладе, нічого не завантажує й не будить warehouse;
  - **спершу метадані:** незмінена країна WFP коштує один маленький запит, CSV не качається;
  - **перевірка форми на вході:** HTML-сторінка з помилкою не потрапляє в landing; збій одного джерела не зупиняє інші;
  - **завантаження CSV за іменами колонок:** `PARSE_HEADER` + `MATCH_BY_COLUMN_NAME` + `INCLUDE_METADATA`; ті самі COPY працюють і з internal stage, і як тіла pipe;
  - **SQL для шляху й версій, Python для одиниць і курсів:** країна, версія й останній файл — у view з `QUALIFY DENSE_RANK()` (рівно один файл, навіть якщо версію завантажили двічі); Snowpark робить одиниці й курси;
  - **курс:** ECB, де він публікується (USD, INR, TRY), інакше зважений неявний курс WFP (сума місцевих цін / сума USD-цін за місяць). На кожному рядку є `FX_SOURCE`, а там, де є обидва курси, — різниця між ними;
  - **одиниці:** `parse_unit` у Python і тестах. `90 KG`, `500 ML`, `200 G` переводяться в кг або л; штуки й послуги зберігаються, але не потрапляють у факти «за кг»;
  - **перебудова поруч і SWAP:** `CREATE TABLE ... LIKE`, append, `ALTER TABLE ... SWAP WITH` — читач бачить або стару, або нову таблицю;
  - **два семантичні шари:** семантичне view для SQL і Cortex Analyst, DAX для звіту; перевірка паритету в SQL і ручна звірка картки в Power BI;
  - **окремі warehouse `P11_BI_WH` і сервісний користувач `P11_POWERBI_SVC`** (key pair, `DEFAULT_NAMESPACE`), Import замість DirectQuery.
- **Знахідки на живих даних (2026-11-10):**
  - WFP CSV на HDX — повна історія країни, яку замінюють цілим файлом. Рядків: Kenya 29 298, Nigeria 91 216, India 216 151, Türkiye 14 562. Дата завжди 15-те число місяця;

  - 98,1% рядків (KEN, NGA, IND, TUR) можна звести до кг або л; решта — `Unit`, `30 pcs`, `Head`, `kWh`, `Course`, `Cubic meter`…;
  - `usdprice` округлено до центів: 70% рядків Індії менші за 1 USD, тож окремий рядок дає курс із похибкою до ~2%;
  - зважений курс WFP проти ECB: INR у межах −0,85…+0,58%, TRY — до 0,15% (травень–жовтень 2026);
